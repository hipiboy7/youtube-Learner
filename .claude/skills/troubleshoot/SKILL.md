# 트러블슈팅 기록

문제를 **해결한 직후**에 쓴다. 나중에 쓰면 실제 출력을 잃고 기억으로 쓰게 되어 어긋난다
(`CLAUDE.md` 4절 — *"오류 메시지를 문서에 인용할 때는 실제 출력을 복사한다"*).

## 언제 쓰나

| 쓴다 | 쓰지 않는다 |
|---|---|
| YouTube가 429·차단을 냈고 대기·간격·제공자로 복구했다 | 오타 수정 |
| 원인 찾는 데 10분 이상 걸렸다 | 테스트 1건 실패 → 바로 고침 |
| **문서와 실제 동작이 달랐다** (yt-dlp 옵션, HF 캐시, Windows 경로…) | 이미 `P*_검토서_TechSpike`에 상세히 적은 것 → 한 줄 + 링크만 |
| **오류 없이 조용히 잘못되던 것**을 잡았다 (중복 행, 디스크 폭증, 빈 세그먼트) | 설계 판단 변경 (그건 정정 이력) |
| 같은 실수를 두 번째 했다 | |

**조용히 잘못되는 유형은 반드시 쓴다.** 소리를 내며 죽는 건 다음 사람도 바로 안다.
조용한 건 기록이 없으면 몇 주를 헤맨다.

## 어디에

`docs/internal/검토서_트러블슈팅.md` **한 파일에 누적**한다. Phase별로 나누지 않는다 — 유지보수
담당자는 "어느 Phase였나"가 아니라 "이 증상이 뭐였나"로 찾는다.

- 파일이 없으면 아래 머리를 붙여 만든다
- 있으면 **1절 색인 표에 한 줄 추가** + **말미에 항목 추가**. 기존 항목은 고치지 않는다
- 번호는 `T-001`부터 순번. 재사용하지 않는다

`CLAUDE.md` 9절 DocType — `검토서` = "정규 4단계 밖의 점검·조사". 트러블슈팅이 여기 해당한다.

## 형식 (이 순서 그대로)

```markdown
## T-0NN · <증상을 한 줄로> · YYYY-MM-DD

| 항목 | 내용 |
|---|---|
| **증상** | 사용자가 보는 것. **실제 출력을 그대로** |
| **환경** | Phase, 브랜치, 외부 상태 (bgutil 스크립트 유무·Node 버전·회선·yt-dlp 버전) |
| **원인** | 진짜 원인. "~인 것 같다"면 그렇게 쓴다 |
| **조치** | 무엇을 바꿨나. 커밋 해시 |
| **재발 방지** | 코드·테스트·검사(check_env/verify_docs)·문서 중 무엇으로 막았나. 없으면 "없음 — 이유" |
| **확인 방법** | 다음 사람이 같은 증상인지 판별하는 명령 1~2줄 |
| **관련** | TechSpike·요구사항·보류 결정 링크 |

### 왜 이런 일이 생겼나
(2~5줄. 다음 사람이 같은 함정을 피하려면 원인의 **구조**를 알아야 한다)
```

**"재발 방지"가 비어 있으면 그 항목은 미완이다.** 기록만 하고 막지 않으면 같은 일이 난다.
막을 수 없다면 왜 못 막는지 적는다 — 그것도 정보다.

## 파일 머리 (최초 생성 시)

```markdown
# 검토서 — 트러블슈팅 기록

- 용도: 유지보수 담당자가 "이 오류 본 적 있나"를 찾는 곳
- 규칙: 해결 직후 기록. 실제 출력 인용. 기존 항목은 고치지 않고 새 항목으로 정정
- 작성: `.claude/skills/troubleshoot/SKILL.md`에 따라 메인이 직접

## 1. 색인

| # | 증상 | 원인 한 줄 | 일자 | Phase |
|---|---|---|---|---|

## 2. 항목
```

## 쓰고 나서

1. `.\backend\.venv\Scripts\python.exe scripts\verify_docs.py --path docs/internal/검토서_트러블슈팅.md` — 링크·경로 확인
2. 색인 표와 항목 번호가 맞는지 확인
3. 그 Phase의 `P*_검토서_SelfReview.md`가 있으면 "발견 사항"에서 `T-0NN` 참조를 건다.
   두 곳에 상세를 중복해 쓰지 않는다 — 검토서는 링크, 상세는 여기
4. `check_env`로 잡을 수 있는 유형(도구 부재·경로·버전)이면 **검사 항목을 추가**하는 것이 재발 방지다

## 예 — Phase 0에서 실제로 있었던 것

```markdown
## T-001 · PO 토큰 제공자가 "unavailable" — pip 설치만으로는 동작하지 않음 · 2026-09-14

| 항목 | 내용 |
|---|---|
| **증상** | `[debug] [youtube] [pot] PO Token Providers: bgutil:http-2.0.0 (external), bgutil:script-node-2.0.0 (external, unavailable), …` + `WARNING: [pot:bgutil:http] Error reaching GET http://127.0.0.1:4416/ping` |
| **환경** | Phase 0 TechSpike, impl-phase0, `pip install bgutil-ytdlp-pot-provider` 직후, Node 24 |
| **원인** | pip 패키지는 yt-dlp **플러그인**만 담는다. 토큰 생성은 Node 스크립트(`server/build/generate_once.js`)가 하며 저장소를 clone해 `npm ci && npx tsc`로 빌드해야 생긴다 |
| **조치** | `~/bgutil-ytdlp-pot-provider/server` 빌드 → `Retrieved a gvs PO Token for web client` 확인 |
| **재발 방지** | `check_env`가 스크립트 실재·Node 버전을 검사(P0). 설정 `BGUTIL_SCRIPT_PATH` 명시. P4 배포물에 빌드 산출물 동봉 |
| **확인 방법** | `yt-dlp -v --js-runtimes node --skip-download <url>` 출력에서 `script-node-2.0.0 (external)` 뒤에 `unavailable`이 없어야 한다 |
| **관련** | `docs/internal/P0_검토서_TechSpike.md` 3.3절 |

### 왜 이런 일이 생겼나
"pip로 설치했다 = 동작한다"는 가정. 플러그인은 외부 실행기를 **호출**만 하고, 실행기는 다른 생태계(Node)에 있다.
두 생태계에 걸친 도구는 설치 단계가 둘이다. 설치 직후 `-v` 로그의 provider 목록을 확인하는 것이 유일한 판별법이다.
```
