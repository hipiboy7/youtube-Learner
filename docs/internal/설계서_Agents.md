## 1. 왜 에이전트/스킬을 두나

이 프로젝트는 문서가 코드보다 많다(Phase당 문서 6종). 사람이 매번 전체를 다시 읽는 것은 지켜지지 않는 규칙이고, 메인 컨텍스트가 수천 줄을 매번 읽으면 작업 컨텍스트를 잃는다.
그래서 **읽기 전용 검사**는 에이전트에, **맥락이 필요한 기록**은 스킬(메인이 직접 실행하는 절차)에 둔다.

| 종류 | 이름 | 하는 일 | 호출 시점 | 도구 | 모델 |
|---|---|---|---|---|---|
| 에이전트 | `doc-consistency` | 변경 한 문장을 받아 문서 전체에서 모순 서술을 찾아 **목록만** 반환. 고치지 않는다 | 리뷰·판단 변경 반영 직후, Phase 종료 루틴 ① | Read·Grep·Glob·Bash | sonnet |
| 스킬 | `troubleshoot` | 트러블 해결 직후 `docs/internal/검토서_트러블슈팅.md`에 T-0NN 기록 | 외부 장애 복구·10분+ 디버깅·문서≠실제·조용한 오류 | (메인) | (메인) |

## 3. 모델 배정과 승격 규칙

- `doc-consistency`는 **sonnet**으로 시작한다. 읽고 대조하는 일이라 비용 대비 충분하다고 가정한다.
- **처음 2~3회는 메인이 결과를 독립 재검토**한다(CLAUDE.md 4절). 놓친 어긋남이 1건이라도 나오면 모델을 **opus 이상으로 올리고 되돌리지 않는다.** 검사원이 놓치는 것을 알면서 쓰는 것은 검사가 없는 것보다 나쁘다(무시되는 관문).
- 승격·실행 기록은 아래 5절에 남긴다.
- **2026-09-14 승격**: 첫 실행에서 숫자 대조 2건을 놓쳐 `model: opus` 로 올렸다. 되돌리지 않는다.

## 4. 만들지 않은 것과 이유

|---|---|
| `report-writer` | AI 인증 심사 결과보고서 양식 전용. 우리는 심사 대상이 아니다 |
| `prompt-finest` | 심사 제출용 프롬프트 회고·압축. 우리 프롬프트는 이력 그대로 보존하면 충분하다. 필요해지면 그때 |
| Phase별 코드 생성 에이전트 | 코드는 메인이 설계서를 보며 쓴다. 에이전트가 쓰면 문서↔코드 추적성(docstring 규약)이 깨지기 쉽다 |
| 실호출 검증 에이전트 | 실호출은 TechSpike·테스트결과서 5절에 **메인이 실제 출력을 복사**하는 절차다. 위임하면 "복사"가 "요약"이 된다 |
