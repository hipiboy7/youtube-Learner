## T-001 · PO 토큰 제공자가 "unavailable" — pip 설치만으로는 동작하지 않음 · 2026-09-14

| 항목 | 내용 |
|---|---|
| **증상** | `[debug] [youtube] [pot] PO Token Providers: bgutil:http-2.0.0 (external), bgutil:script-node-2.0.0 (external, unavailable), bgutil:script-deno-2.0.0 (external, unavailable)` / `[debug] [youtube] [pot:bgutil:script-node] Script path doesn't exist: C:\Users\SYSADMIN\bgutil-ytdlp-pot-provider\server\build\generate_once.js` / `WARNING: [youtube] [pot:bgutil:http] Error reaching GET http://127.0.0.1:4416/ping (caused by TransportError).` |
| **환경** | Phase 0 TechSpike, `impl-phase0`, `pip install bgutil-ytdlp-pot-provider`(2.0.0) 직후, Node v24.14.0, yt-dlp 2026.08.19 |
| **원인** | pip 패키지는 yt-dlp **플러그인**(`yt_dlp_plugins/extractor/getpot_bgutil_*.py`)만 담는다. 토큰 생성은 Node 스크립트 `server/build/generate_once.js`가 하며, 플러그인은 기본 경로 `~/bgutil-ytdlp-pot-provider/server`에서 그것을 찾는다. 저장소를 clone해 `server/`에서 `npm ci && npx tsc`를 해야 `build/`가 생긴다 |
| **조치** | `git clone --depth 1 https://github.com/Brainicism/bgutil-ytdlp-pot-provider` (홈 디렉토리) → `cd server && npm ci && npx tsc` → 재실행 시 `[youtube] [pot:bgutil:script-node] Generating a gvs PO Token for web client via bgutil script` / `Retrieved a gvs PO Token for web client` |
| **재발 방지** | 검사 — `check_env`가 `BGUTIL_SCRIPT_PATH`(기본 위 경로) 실재와 `node --version ≥ 20`을 검사한다(P0 FR). 설정 — `.env.example`에 키와 빌드 절차 주석. 배포 — P4에서 빌드 산출물을 앱 리소스로 동봉(설계서_Architecture 3.2절) |
| **확인 방법** | `backend\.venv\Scripts\python.exe -m yt_dlp -v --js-runtimes node --skip-download <영상 URL>` 출력의 `PO Token Providers:` 줄에서 `script-node-2.0.0 (external)` 뒤에 `unavailable`이 **없어야** 한다 |
| **관련** | `docs/internal/P0_검토서_TechSpike.md` 3.3절, `docs/설계서_Architecture.md` 3.2절 |

### 왜 이런 일이 생겼나
"pip로 설치했다 = 동작한다"는 가정이 깨졌다. 플러그인은 외부 실행기를 **호출**만 하고, 실행기는 다른 생태계(Node)에 있다.
두 생태계에 걸친 도구는 설치 단계가 둘이다. 그리고 실패가 **조용하다** — 제공자 없이도 이날은 자막이 받아져서 `-v` 로그를 보지 않으면 모른다.
설치 직후 `-v` 로그의 provider 목록을 확인하는 것이 유일한 판별법이고, 그래서 `check_env`에 넣었다.

## T-003 · 자막 `en` 요청 HTTP 429, 명령 전체 실패 · 2026-09-14

한 줄 + 링크(상세는 TechSpike): 이 영상의 원어는 `ko`(자동자막 `ko-orig`)이고 `en`은 유튜브 **번역** 트랙이라 요청 즉시 `ERROR: Unable to download video subtitles for 'en': HTTP Error 429: Too Many Requests`가 났다(재시도 동일). yt-dlp는 한 언어 실패로 **명령 전체를 종료 코드 1**로 끝낸다(ko 파일은 저장됨).
→ 규칙: 원어 트랙만 요청, 언어별 개별 요청, 429 백오프(`CLAUDE.md` 8절). 재발 방지는 P2 Provider 설계·테스트. 상세: `docs/internal/P0_검토서_TechSpike.md` 3.2절.

## T-005 · PowerShell 스크립트가 한글 문자열 자리에서 구문 오류 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | 사용자가 `.\scripts\dev_proto.ps1` 실행 → `At D:\claude\youtubeLearner\scripts\dev_proto.ps1:14 char:121 + ... í"„ë¡ íŠ¸: http://localhost:5173 (ê°ê° ìƒˆ ì°½ì—` — 한글이 깨진 채 파서 오류 |
| **환경** | Windows PowerShell 5.1(사용자 콘솔), 프로토타입 브랜치. 같은 파일을 Claude 세션은 Git Bash 에서 `powershell -File` 로 실행해 통과했었다(그때는 한글이 문자열 밖 주석에만 있어 우연히 파싱됨) |

| **조치** | `scripts/check_env.ps1`·`scripts/dev_proto.ps1` 앞에 UTF-8 BOM(`EF BB BF`) 추가. `[System.Management.Automation.Language.Parser]::ParseFile` 로 두 파일 파서 오류 0 확인, `check_env.ps1` → READY 재확인 |
| **재발 방지** | 규칙 — `.ps1` 은 **UTF-8 BOM** 으로 저장한다(한글 주석·문자열이 있으면 필수). 검사 — `verify_docs` 에 "`scripts/*.ps1` 첫 3바이트가 BOM 인가" 항목 추가는 P1 보류 후보. `.gitattributes` 는 줄끝만 다루므로 BOM 은 강제하지 못한다 |
| **확인 방법** | `powershell -NoProfile -Command "[System.Management.Automation.Language.Parser]::ParseFile('scripts\dev_proto.ps1',[ref]$null,[ref]$e)|Out-Null; $e.Count"` → `0`. 또는 `Format-Hex scripts\dev_proto.ps1 | Select -First 1` 첫 바이트 `EF BB BF` |
| **관련** | `docs/internal/검토서_Prototype.md` 2절(실행 방법), T-004(도구 기본 가정을 검토하지 않은 같은 유형 — 여기서는 "UTF-8 이면 어디서나 읽힌다"는 가정) |

### 왜 이런 일이 생겼나
검증은 Claude 세션의 셸(Git Bash → `powershell -File`)에서만 했고, 사용자의 실제 콘솔(Windows PowerShell 5.1)에서 하지 않았다. 같은 파일이 실행 주체에 따라 다르게 읽힌다.
**문서에 적은 명령은 독자의 환경에서 그대로 실행해 확인한다**(CLAUDE.md 4절) — 여기서 "독자의 환경"에는 콘솔 인코딩도 포함된다.

## T-006 · 프로토타입 재실행 뒤에도 프롬프트 저장 404, 스크립트 복사 무반응 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | 사용자: "재실행해서 봤는데, 프롬프트 편집해서 저장해도 저장이 안돼. 그리고 스크립트 복사해도 해당 내용 복사가 안되고." 서버 확인: `GET /proto/settings/summary_prompt → 404`, 8765 리스너 PID 6276 StartTime 20:24(코드 변경 전) |
| **환경** | 프로토타입 브랜치, 사용자가 `dev_proto.ps1` 창을 닫고 다시 실행한 뒤. Claude 는 8766 별도 인스턴스로만 새 코드를 검증했었다 |
| **원인** | (1) `Start-Process powershell -NoExit … uvicorn` 으로 띄운 창을 닫아도 **uvicorn 자식 프로세스가 살아남아** 같은 포트에서 옛 코드로 계속 응답했다. 새 창의 uvicorn 은 포트 충돌로 바로 죽었을 것이고 사용자는 알 수 없었다. (2) 복사 함수가 `navigator.clipboard.writeText` 실패를 잡지 않아 **조용히 실패**했다. (3) Claude 는 사용자 화면이 붙는 8765 가 아니라 8766 에서만 검증해 사용자 환경의 상태를 보지 못했다 |
| **조치** | 옛 프로세스 종료 후 새 코드로 8765 재기동. `dev_proto.ps1` 이 시작 전 8765·5173 리스너를 종료. `/health` 에 `version`(proto-2) 을 넣고 화면이 불일치 시 상단 경고. 복사는 클립보드 API → execCommand 폴백 → 수동 복사 상자, 실패 사유를 알림으로. 커밋 `b59d5b0` |
| **재발 방지** | 스크립트 — 잔존 리스너 정리(코드). 화면 — 버전 불일치 경고·실패 사유 표시(코드). 절차 — **사용자가 쓰는 포트·프로세스에서 검증**한다: 검증 전 `Get-NetTCPConnection -LocalPort 8765` 로 PID·StartTime 을 확인해 코드 변경 시각보다 늦게 시작된 프로세스인지 본다. P4 사이드카 설계에 "부모 종료 시 자식 종료(프로세스 트리)" 요구가 이미 있다 — 같은 문제의 배포판 |
| **확인 방법** | `curl http://127.0.0.1:8765/health` 의 `version` 이 코드의 `PROTO_VERSION` 과 같은가. 화면 상단에 빨간 경고가 없는가 |
| **관련** | `docs/internal/검토서_Prototype.md` 7절, `docs/설계서_Architecture.md` 8.2절(사이드카 종료 시 `taskkill /T`), T-005 |

### 왜 이런 일이 생겼나
"프로세스를 재시작했다"는 사용자의 행동과 "새 코드가 응답한다"는 사실 사이에 검증이 없었다. 조용히 실패하는 두 지점(잔존 프로세스, 예외를 삼키는 복사)이 겹쳐 사용자는 "저장 안 됨·복사 안 됨"만 봤다.
**실패는 소리를 내야 하고, 재시작은 버전으로 증명해야 한다.** 배포판(P4 사이드카)에서 같은 구조가 반복되므로 설계 요구로 이미 올라가 있다.
